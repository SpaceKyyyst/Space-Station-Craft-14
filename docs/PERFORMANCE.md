# Производительность сервера

Просадка до 3 TPS при 20 игроках сообщена командой разработки. Профиль этого
сервера и его карта в локальных проверках отсутствовали. Число игроков само
по себе не определяет стоимость тика: важны загруженные чанки, устройства,
движение газа, изменения кабелей, сущности и состав модов.

## Изменения горячих путей

| Подсистема | Поведение |
| --- | --- |
| Атмосфера | Ленивые ячейки, актуальная проницаемость при переносе, сон равновесных ячеек, очередь с бюджетом 8 регионов × 256 ячеек каждые 4 тика |
| Частицы газа | Адресная отправка: нет повторной общей рассылки внутри цикла игроков; стоимость рассылки O(V × P), а не O(V × P²) |
| Электросеть | Индекс владельца кабеля; пересборка затронутых компонент вместо всех сетей измерения; изменения объединяются до серверного тика |
| ID-карты | Таблица типов и кэш масок доступа по неизменяемым компонентам; повторная проверка слотов не декодирует прежний NBT |
| Гравигенераторы | Один расчёт состояния; промежуточные обновления и частицы раз в 4 тика, переход blockstate отправляется сразу |
| Критическое состояние | Пакет способностей отправляется при изменении разрешения строительства |
| Отложенная работа | Очередь отдельного сервера, до 512 новых и 512 готовых задач за тик, не более 65 536 ожидающих задач; FIFO для одинакового срока, ошибки задач журналируются отдельно |

Новая топология сохраняет прежние радиусы подключения устройств. Пересборка
обходит изменённые позиции и затронутые кабели; очень большая единая сеть всё
ещё может вызвать длинный тик. Диагностическое чтение мультитулом не запускает
полную пересборку. Индекс кабелей по чанкам обслуживает загрузку и выгрузку:
проверяются девять ближайших чанков, включая устройства на границе, без обхода
всех кабелей мира.

Проверка ID-карт сохраняет немедленное снятие доступа после удаления карты.
Вложенные контейнеры теперь обходятся; для одного корневого предмета установлены
пределы 16 уровней и 512 предметов. Предметы за пределом обхода не дают доступа.
Замена компонентов карты или контейнера инвалидирует результат. Кэш использует
слабые ключи и не удерживает удалённые ItemStack.

## Границы потоков

Мир, чанки, сущности, инвентари и топология изменяются только в серверном потоке.
`ServerTaskScheduler.submit(server, delay, action)` позволяет фоновому коду
передать применение результата в поток конкретного работающего сервера.
После остановки сервера или при заполненной очереди отправка возвращает false.
Лимит учитывает входящие и уже запланированные задачи, в том числе при нескольких
производителях. Совместимый
`Ssc14Mod.queueServerWork` предназначен для вызова из серверного потока и при отказе
выбрасывает `RejectedExecutionException`, чтобы не терять задачи молча.

Задачи, поставленные во время выполнения очереди, принимаются на следующем
тике. При переполнении бюджета они остаются в очереди; задержка начинает
отсчитываться при принятии задачи планировщиком. Бюджет ограничивает число
задач, а не время отдельной тяжёлой задачи. Производитель должен обработать отказ,
не повторяя отправку в бесконечном цикле. Отдельный пул фоновых потоков
для операций Minecraft не создаётся.

При превышении бюджета атмосферы скорость её симуляции снижается без потери
необработанных ячеек. Это защита основного тика, а не гарантия 20 TPS.

## Профиль боевого сервера

На сборке с этими изменениями оператор с правами владельца может выполнить:

1. `/jfr start` во время обычной игры с воспроизводимой нагрузкой.
2. Воспроизвести лаги в течение 60–120 секунд, записав число игроков и действия.
3. `/jfr stop`; путь к файлу записи появится в ответе команды.

Событие `ssc14.TickPhase` содержит `subsystem`, `workItems` и длительность:
`atmosphere`, `energy_topology`, `energy_simulation`, `player_access`.
Пересборка топологии вложена в расчёт энергии: их времена нельзя просто
складывать. `workItems` — размер очереди/инвентаря на входе, не обязательно число
фактически обработанных элементов. Для energy_simulation поле равно нулю;
для energy_topology — число использованных шагов текущего тика на входе.

Сравнивать нужно одинаковые карту, оборудование, состав модов и сценарий.
Оценивать среднее и высокие перцентили длительности тика, сборку мусора,
загрузку чанков, CPU-профиль и длительности подсистем. Локальные GameTest и
JUnit подтверждают проверенные правила и ограничения очередей, но не
воспроизводят сервер команды с 20 живыми игроками.

## Большие электросети

Все вызовы пересборки одного мира делят бюджет: максимум 128 шагов и целевые
2 мс за игровой тик, с чередованием HV/MV/LV. Ограничение времени кооперативное:
начатый шаг не прерывается. Бюджет отдельный для каждого измерения.

Изменение кабеля сразу запрещает расчёт затронутой сети. На первом следующем
энергетическом тике лампы выключаются и заряд не расходуется. До завершения
обхода отключена вся затронутая компонента, включая исправную сторону разрыва.
Независимые готовые сети продолжают работать. Старые компоненты удаляются после
обработки отключения. Повторное изменение отменяет незавершённое поколение.

Без новых изменений обход занимает O(V + E + S), где S — исходные позиции;
поиск устройств на кабеле ограничен постоянным объёмом. Память O(V + S).
Публикация и удаление компонента используют индекс: ожидаемое O(1).
Событие чанка посещает компоненты девяти соседних чанков, а не каждый кабель.
При непрерывном редактировании затронутая сеть может оставаться выключенной.
Симуляция потребителей и изменение блоков ламп пока не имеют отдельного
временного бюджета. Доступ к миру остаётся в серверном потоке.

## Проверка через spark

Для Minecraft 26.1 доступен [spark 1.10.172 для NeoForge](https://modrinth.com/mod/spark/version/1.10.172-neoforge).
Сравнивать одинаковую карту и нагрузку до и после изменения:

1. `/spark profiler start --timeout 120` — обычная работа и разрывы большой сети.
2. Отдельная запись: `/spark profiler start --timeout 120 --only-ticks-over 50`.
3. Сравнить серверный поток, EnergyTopologyService, EnergySimulationServer,
   загрузку чанков и GC; записать размер сети и число игроков.

Для фоновых потоков доступен `--thread *`, для выделений памяти — `--alloc`.
[Документация команд](https://spark.lucko.me/docs/Command-Usage).
Spark измеряет нагрузку; правильность отключения проверяется отдельно игровыми тестами.

## Постоянный расчёт энергии и лампы

Симулятор не копирует наборы источников и потребителей каждый тик. Удаление
невалидных устройств выполняется через итератор; статистика источников собирается
в том же проходе, что и доступная мощность. При нулевом потреблении распределение
списаний не запускается, неизменившийся заряд не помечает блок как изменённый.

`LampTickBatch` хранит снимок каждой встреченной лампы только на текущий тик.
Общие для нескольких сетей лампы оплачиваются один раз. Постоянного кэша
состояния лампы нет: поломка, извлечение лампы и разряд видны на следующем тике.
Установившееся состояние требует одного чтения блока на уникальную лампу,
без отправки повторных изменений. При переключении блок перечитывается перед
записью для защиты от соседних обновлений. Отключение не откладывается в очередь.

Расчёт остаётся O(S + C) по источникам и связям потребителей; временная память
ламп — O(L) по уникальным лампам. Число кабелей не влияет на расчёт готовой сети.
Мультитул обновляется каждые четыре тика (5 раз в игровую секунду).
Показания относятся к кабелю под прицелом, как в основной ветке; сеть находится
через индекс владельцев за ожидаемое O(1), без обхода всех сетей или кабелей.

Одновременное переключение очень большого количества ламп всё ещё создаёт
обновления блоков и освещения. Жёсткого бюджета этой операции нет, чтобы
сохранить отключение всех потребителей на первом энергетическом тике.
Выигрыш в миллисекундах и TPS требует профиля на рабочей карте.
