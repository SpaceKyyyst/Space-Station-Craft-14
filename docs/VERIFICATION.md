# Проверки и непрерывная интеграция

## Локальные проверки

```powershell
.\gradlew.bat domainTest
.\gradlew.bat checkstyleMain
.\gradlew.bat pmdMain methodMetrics
.\gradlew.bat build
.\gradlew.bat runGameTestServer
```

На Linux/macOS используется `sh ./gradlew` с теми же именами задач.

| Проверка | Что покрывает | Результат |
| --- | --- | --- |
| `domainTest` | Газовые смеси и реакции, очередь атмосферы, компоненты энергосетей, бюджеты, реагенты, ограничения сетевых данных, броня | `build/reports/tests/domainTest/index.html` |
| `checkstyleMain` | Выделенные доменные пакеты из `sourceSets.domain` | `build/reports/checkstyle/main.html` |
| `pmdMain` | Все production Java-файлы: некорректные null-проверки, сравнения строк/NaN, индексы циклов, потерянные результаты immutable-операций и другие проверки из `config/pmd/correctness.xml` | `build/reports/pmd/main.html` |
| `methodMetrics` | Цикломатическая сложность исполняемых методов и конструкторов | `build/reports/pmd/method-metrics.html` |
| `test` | Проверки адаптеров с Minecraft-зависимостями | `build/reports/tests/test/index.html` |
| `build` | Компиляция всего мода, тесты, Checkstyle, PMD, отчёт сложности, упаковка | `build/libs/` |
| `runGameTestServer` | Сценарии на настоящем сервере Minecraft с загруженным модом | `build/test-results/gameTest/`, `build/gameTest/run/logs/` |

Доменные исходники компилируются без Minecraft-зависимостей из тех же файлов, которые используются при сборке мода. Точное число выполненных тестов и результаты доступны в JUnit-отчёте конкретной сборки.

Checkstyle пока охватывает выделенный домен, а не весь сгенерированный код. При добавлении независимой подсистемы её исходники включаются в `sourceSets.domain` в `build.gradle`; тесты размещаются в `src/domainTest/java`.

PMD проверяет весь production-код без исключения генерируемых каталогов и останавливает сборку при нарушениях выбранных правил. Отчёт `methodMetrics` намеренно включает методы с любой сложностью; его записи не являются ошибками и не означают ручную проверку поведения каждого метода. Абстрактные методы без тела и лямбды не представлены как самостоятельные методы. Эти проверки не подтверждают корректность игровой логики без тестовых сценариев.

## Проверки инфраструктуры

Для Python-скриптов требуется Python 3.11 или новее:

```sh
python .github/scripts/test_gametests.py
python .github/scripts/check_project.py
```

`test_gametests.py` проверяет обработку отсутствующих и неуспешных серверных результатов.
`check_project.py` сверяет версию, mod ID, наличие файлов сборки и отсутствие
локальных файлов инструментов среди отслеживаемых Git путей. Проверка не читает
и не изменяет игнорируемые или неотслеживаемые файлы.

## Автоматизация

GitHub Actions, Dependabot и автоматический release pipeline удалены. Все проверки
запускаются локально командами из раздела выше; публикация релиза выполняется
только вручную после отдельного решения сопровождающего.

После сборки запускается отдельный GameTest-сервер. Проверка XML требует
выполнения всех обязательных сценариев и отклоняет отсутствующий отчёт,
ошибки и пропуски. Тестовые классы и структуры из `src/gameTest/` не входят
в публикуемый JAR. Для адаптерных JUnit-тестов включена среда NeoForge.
Обычный `build` не запускает GameTest-сервер; локально он вызывается отдельно.

Автоматических запусков, push-триггеров и ручного workflow-триггера нет.

## Публикация релиза

Публикация выполняется отдельным заданием после успешной сборки `main`. Pull request и другие ветки не публикуют релизы.

- Загружается JAR, собранный предыдущим заданием, без повторной сборки.
- Тег содержит имя артефакта, номер запуска и короткий SHA коммита.
- В релиз добавляются JAR и `SHA256SUMS.txt`.
- Повторный запуск проверяет SHA существующего тега, обновляет артефакты и завершает публикацию оставшегося черновика.
- Если тег указывает на другой коммит, публикация завершается ошибкой.

В форке релизы создаются в самом форке. Для работы pipeline в конкретном репозитории GitHub Actions должны быть разрешены его владельцем.

## Игровое тестирование

Автоматические тесты не заменяют запуск Minecraft. Сценарии зависят от изменённой подсистемы:

| Область | Что проверить в игре |
| --- | --- |
| Загрузка мода | Клиент и выделенный сервер с обязательными зависимостями |
| Сохранения | Сохранение и повторная загрузка тестового мира |
| Броня | Пустые слоты, разные предметы Curios, несколько источников сопротивления |
| Атмосфера | Пустая ячейка, нагрев/охлаждение, расход и образование газов |
| Энергетика | Соединение и разрыв кабелей, несколько источников, выгрузка чанков |
| Сеть и интерфейс | Несколько игроков, синхронизация, недопустимые действия клиента |

Успешный CI подтверждает только выполненные автоматические проверки. Игровые результаты следует оценивать для конкретной версии и набора изменений.


Сценарии audit из PR производительности включены в общий sourceSet gameTest
наряду с тестами основной ветки. Оба набора запускаются через runGameTestServer;
config/gameplay-tests.init.gradle сохраняет совместимый псевдоним runGameplayTest.
В проверках топологии учитывается её постепенная готовность, а отключение
ламп и отсутствие расхода после разрыва проверяются отдельно на первом тике.
